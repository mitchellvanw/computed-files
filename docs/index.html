Guides and sensors

Birgitta Böckeler splits the controls around a coding agent into two kinds. Guides are feedforward. They steer the agent before it acts. Sensors are feedback. They look at what the agent did and give it a signal to correct against. A CLAUDE.md or AGENTS.md is a guide. The harness injects it ahead of every task, and the agent takes it as an accurate description of the repo.

A guide is only useful while it matches the code. Nothing in the loop notices when the tree or the module table drifts, so the agent starts each task with a picture that was accurate a month ago. A wrong guide does more damage than none, because the agent does not second-guess it.

The two sums add the missing sensor. computed check compares them and exits 1 when a region no longer matches its inputs. It never runs a generator, so it fits in a pre-commit hook and in CI. The context file stays a guide. Its freshness becomes something the harness can measure.

The vocabulary is from Harness engineering for coding agent users, Birgitta Böckeler on martinfowler.com, April 2026.

Two sums, no state

Tools that rewrite a marked span already exist. cog, mdsh, markdown-magic. They store a checksum of what they wrote, at best. None of them store what they read, so "is this fresh" means running every generator again. The comparison is below.

Every closer here carries both. The input sum hashes the opener line plus a snapshot of the inputs. The output sum hashes the body. Together they answer both questions from the rendered file alone, with no cache directory that a fresh clone would lose.

Why not cog, or mdsh, or markdown-magic?

They all rewrite the span between two comments, and they all do it well. What none of them write down is what the span was computed from. So the only way to ask "is this still right" is to run everything again.

Where they are ahead

markdown-magic has a fileTree transform and a plugin API. cog runs on any text file and has done so for twenty years. Both have users we do not. cog's checksum is where the output sum comes from, and org-babel's :cache, a hash of the block and its arguments, is the nearest thing to the input sum. We have two loaders and read markdown only.

Why the second sum matters

A rerun is fine for a table of contents. It is not fine for a shell command in a file an agent reads before every task. The rerun needs the generator, its runtime, and permission to execute text from a checkout. CI has none of those, so nobody checks. Two hashes in the closer make the check a read.

Six states a region can be in

Every state is derived from the file and its inputs alone, in this order. No loader runs to find out.

Hand edits are refused, not reverted

An agent that edited a region had a reason. Overwriting it on the next run loses that work without a trace. The region stays, the run exits 1, and regenerating takes an explicit --force or deleting the sum.

A failed loader keeps the last good body

Deleting an input does not blank the region. Body and sums stay as they were, the run exits 1 so CI notices, and restoring the file repairs it on the next run.

Two loaders, two sinks

A loader returns text plus the snapshot the input sum is taken over. A sink turns that text into the body that lands in the file. Each loader has a default sink, and an opener can pick the other with as=.

Relative paths resolve against the directory of the file holding the marker, not the repository root or the shell's working directory. So a region reads the same from a pre-commit hook, from CI, or from a terminal, and moving the file moves its regions with it.

An exec region runs only in a repository you have trusted on this machine with computed trust. The grant lives in your config directory, so nothing inside a clone can grant itself. CI passes run --trust for one invocation. check never runs a loader, so it needs no trust at all.

One file, two owners

There is no template rendered to a sibling. The file you commit is the file the tool edits, and the tool owns the region bodies and nothing else. Everything outside a marker pair is yours, and a run never touches it.

Inside a region it is the other way round. The output sum hashes the body as written, so run can tell a hand edit from the file alone and refuses to overwrite it. The opener suffix | do not edit; run computed is the only generated-content marker, and it applies to the region, not the file.

Pre-commit runs, CI checks

The pre-commit hook runs computed run. When it rewrites a file the commit fails and you re-stage, the same way rustfmt behaves. CI runs computed check, which compares sums and exits 1 on drift without running anything from the repo.

The hook has to run on every commit, not only when a Markdown file is staged. A change under src/ makes the tree region stale without touching CLAUDE.md, and a filename-filtered hook would never see it.

Every write goes through a temp file and rename(2), and nothing is written when the bytes would be identical. So run twice is a no-op and the mtime never moves. There is no watcher. A daemon is a convenience over run, and it waits until dogfooding shows agents reading stale regions between commits.

.pre-commit-config.yaml

repos:
  - repo: local
    hooks:
      - id: computed
        name: computed run
        entry: computed run
        language: system
        always_run: true
        pass_filenames: false

.github/workflows/ci.yml

- run: cargo build --release
- run: ./target/release/computed check
