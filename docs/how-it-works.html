The markers

A region is the span between two whole-line HTML comments. The first names what fills the region. The second carries the hashes. Anything between them is the body, and the tool owns it.

<!-- computed tree src=. depth=2 name=layout | do not edit; run computed -->
```text
.
├── docs
└── src
```
<!-- /computed in=9f3a1c0b… out=41c0d9e8… -->
In the opening commentMeaning
tree · execThe first word picks what fills the region. There are two.
name=Optional. Reports use it instead of the line number. Unique per file.
as=fence · as=rawHow the text lands in the file. fence wraps it in a code block, raw pastes it as Markdown. Tree defaults to fence, exec to raw.
lang=The language on the code fence. Empty by default.
| do not edit; run computedThe tool adds this suffix when it renders. You do not write it, and the parser ignores it.

A closing comment with no hashes means the region has never been rendered. A closing comment with one hash, an unknown word, a duplicate name, or a region inside another region is a parse error. The file is left alone and the exit code is 2. Markers inside a fenced code block are ignored, which is how this page's examples survive.

The two hashes

in= is a SHA-256 over the opening comment and a snapshot of the inputs. For tree, the snapshot is the list of paths it printed. For exec, it is the bytes of every file named in inputs=. If either changes, the region is stale.

out= is a SHA-256 over the body, byte for byte. If it no longer matches, someone edited the body.

Both live in the closing comment, so a fresh clone carries everything check needs. There is no cache and no sidecar file. The binary's version is not part of either hash, so upgrading does not make every region stale.

Tree and exec

tree

<!-- computed tree src=. depth=2 all dirs -->

Lists a directory the way tree does, without sizes or dates. src= defaults to the file's own directory and depth= to unlimited. all includes dotfiles, dirs lists only directories.

Inside a git repository it skips what .gitignore skips, with no flag to turn that on or off. Names are sorted by byte order so two machines print the same listing.

exec

<!-- computed exec cmd="cargo tree --depth 1" inputs=Cargo.lock -->
<!-- computed exec cmd=date volatile -->

Runs cmd= with /bin/sh -c and pastes its standard output. You must say what the command reads. inputs= takes comma-separated globs, and every matched file's bytes go into the snapshot. volatile says the command has no inputs and should run every time.

The command runs with the file's directory as its working directory, a 30 second limit you can change with timeout=, and LC_ALL=C and TZ=UTC set so its output does not depend on the machine. An exec region only runs in a repository you have trusted. See who may run a command.

Relative paths resolve against the directory of the file holding the marker, not the repository root or the shell's working directory. So a region reads the same from a hook, from CI, and from a terminal, and moving the file moves its regions with it. A path that leaves the repository is an error, because such a region would render differently on every machine.

Before the text lands in the file, line endings become LF and trailing newlines are stripped. A command that prints invalid UTF-8, a control character, or a line that looks like a marker has failed. When a command fails, times out, or exits non-zero, the old body and both hashes stay, its stderr is printed under the region's line, and the run exits 1. Deleting an input does not blank a region.

The states

Four questions, asked in this order. The first one that says no names the state. check asks them and reports. run asks them and then renders every region that is not fresh.

StateWhat it meanscheckrun
freshBoth hashes match.silent, exit 0left untouched
staleThe inputs or the opening comment changed.reported, exit 1rendered
editedThe body no longer matches out=.reported, exit 1refused, exit 1
stale+editedBoth.reported, exit 1refused, exit 1
volatileAn exec region with no inputs and an unedited body.silentrendered every time
unrenderedThe closing comment has no hashes.reported, exit 1rendered, whatever the body holds
untrustedNot a state of the region but of the clone: an exec region in a repository you have not trusted.not a concern, check runs nothingskipped, exit 1

Because check never runs a command, a command whose output changes for the same inputs is invisible until you pass --force. That is the price of a check that needs no runtime and no trust.

Hand edits

The file you commit is the file the tool edits. Outside a marker pair everything is yours and a run never touches it. Inside, the body is the tool's, and an edit there is refused rather than overwritten. The region stays as edited, the whole file is left unwritten, and the run exits 1.

To regenerate, pass --force, which overwrites every edited region in the files you name, or delete both hashes from the closing comment. Editing the opening comment is not a hand edit. It changes in=, so the region is stale and renders on the next run.

The reason to refuse rather than warn is the pre-commit path. A warning from a hook that still writes and exits 0 is an overwrite with a line nobody reads. On CLAUDE.md the editor is usually an agent, and a failed hook is the one signal that reaches it.

Who may run a command

An exec region runs only in a repository you have trusted on this machine. The model is the one direnv and git's safe.directory use.

computed trust            # this repository, on this machine
computed untrust          # take it back
computed run --trust      # this one invocation, for CI

The grant is stored in ~/.config/computed/trust.toml, keyed by the repository root. Nothing inside a checkout can grant itself. In an untrusted clone, run skips every exec region, reports it as untrusted, still renders the tree regions, and exits 1. check never runs a command, so it needs no trust at all.

This defends against one thing: cloning a repository and having computed run execute its commands before anyone has read them. A malicious branch pulled into a clone you already trust runs on the next run, the same as a Makefile or a pre-commit hook would.

Commands and exit codes

run [paths]Render every region that is not fresh and write the files. Exit 1 when it wrote, refused, or a command failed.
run --dry-runPrint the diff each file would get, write nothing. The only place the pending diff is shown.
run --forceAlso overwrite edited regions.
run --trustTreat every file as trusted for this invocation.
check [paths]Report the state of every region. Runs no command. Exit 1 on anything but fresh.
clean [paths]Empty every body and strip the hashes, leaving the markers. The next run rebuilds them.
trust · untrust [path]Grant or revoke exec for the repository containing the path.
-vAlso print the regions that are fine.

With no paths, a command walks the current directory for .md files, skipping what .gitignore skips. A file you name is read whatever its extension.

one line per region, on stderr

CLAUDE.md:12 layout tree stale      written
CLAUDE.md:40 deps   exec edited     refused; run with --force
CLAUDE.md:58        exec untrusted  skipped; run `computed trust`
  • exit 0Nothing to report. Everything is fresh.
  • exit 1The content said no. Drift, a written file, a refused edit, a failed command, an untrusted region.
  • exit 2The tool could not answer. A usage error, a parse error, a path outside the repository, an inputs= glob that matches nothing.

How files are written

Every write goes to a temporary file that is then renamed over the original, keeping its permissions. Nothing is written when the bytes would be identical, so running twice changes nothing and the file's modification time does not move. A file with one refused region is not written at all, even if other regions in it are merely stale. Other files in the same invocation still are.

There is no watch command. Pre-commit runs run and CI runs check, and that has been enough so far. A watcher would sit on top of run and gets built when dogfooding shows agents reading stale regions between commits.
