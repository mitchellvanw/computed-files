# Sums are full SHA-256

Both sums in a closer are SHA-256, written as all 64 lowercase hex characters. The prototype carried a truncated hash as a stand-in; once files carry the closer format it is the hardest thing in the tool to change, so the algorithm and width are fixed now rather than after the first rendered `CLAUDE.md` is committed. What the sums are taken over is unchanged from the spec's sum section. The `sha2` crate is accepted as a dependency: hand-rolled crypto is not worth it, even in a prototype.

## Considered Options

- **Truncated BLAKE3, 16 hex characters** (the stand-in). Rejected: a 64-bit sum is short enough that a collision is worth thinking about, and every reader would have to ask which hash and how much of it. Truncation also invites a second truncation later.
- **Full BLAKE3, 64 hex characters.** Rejected, narrowly: faster, but SHA-256 is what every other tool on a developer's machine can compute from a shell, so a closer can be checked by hand with `shasum -a 256`.
- **Full SHA-256, 64 hex characters.** Chosen. Cost: a closer line about a hundred characters longer than the stand-in, and one dependency. A closer with a 16-character sum is now a malformed-sum parse error, so files rendered by the stand-in are cleaned by stripping their sums before the next `run`.
