Computed Markdown

Keep generated regions of a hand‑written file fresh by computation, not by an agent. What already exists, what to borrow, and why the symlink is the one part of the sketch to drop.

The idea What exists The symlink verdict Freshness and the loop What to borrow Renderers Beyond markdown Decisions

1 · The idea

A template, a renderer, and a file that is always right

The motivating case is the folder tree in a CLAUDE.md. It goes stale the moment a file is added. Asking an agent to fix it costs tokens every time and still depends on the agent noticing. The computational version has four parts: a data source (a directory, a CSV, a SQL query, a shell command), a renderer or sink (a markdown table, a fenced block, a mermaid diagram as text or as an image), a watcher that notices when either the template or the data changes, and a layout that decides where the rendered file lives.

The template is hand‑written prose plus markers that say where computed content goes and what produces it. A process materialises a rendered file from it. The original sketch then symlinks the canonical path to that rendered file. Section 3 tests that last step.

Below is what a region looks like once the tool has been through it. Markers are HTML comments, so GitHub does not render them, prettier leaves them alone if wrapped in its range‑ignore, and Claude Code strips block‑level comments before injecting CLAUDE.md, so they cost no tokens. The tree is this repository's, computed while writing this page.

2 · What already exists

Two axes sort every tool surveyed

Where the output lives, and when the tool runs. Every markdown rewriter sits in one cell: output in the same file, run on demand or in CI. Every live system sits in the opposite corner: separate output, rebuilt on change. Nobody ships a watcher that rewrites the file it watches. The self‑write feedback loop, covered in section 4, is the reason.

Four tools are worth reading in full before writing a line:

  • cog works on any text file. Its markers match anywhere on a line, so //[[[cog and /* [[[cog */ both work, and with -c the closer becomes [[[end]]] (sum: …). Hand‑edited output fails the next run with "Output has been edited!"
  • markdown‑magic already ships a fileTree transform. The exact motivating case, done.
  • org‑babel has the three ingredients together: source expression next to output, output written back into the file, and a SHA1 that skips work. It lacks a daemon and hashes only the block text, not the files the block reads.
  • Observable Framework data loaders decouple the reference, the producer and the freshness rule. Section 5 draws the mechanism.

3 · The symlink verdict

The template model is sound. The link is the weak part.

Nix's result link, home‑manager generations, Stow and Bazel's convenience links all share one shape: the link is the user‑facing handle, the target is immutable per generation, and the link is not the unit of version control. None of them put the link at a path that other tooling treats as source. A CLAUDE.md is exactly such a path.

A hardlink looks like the escape hatch and is not. The renderer publishes atomically by writing a temp file and calling rename(2). That replaces the directory entry, not the inode. The hardlink keeps pointing at the old one. Verified in a scratch repo: after one publish the symlink read the new content and the hardlink still read the old.

Recommendation. Keep template → render. Write the rendered file at the canonical path via temp file and rename(2), commit it, put a generated‑from banner on line one, and ship a check command that fails CI on drift. This is the sketch minus the link, and it is what gomplate, quarto, mermaid‑cli and Style Dictionary all do. Keep the symlink layout as a per‑file opt‑in for outputs that really are local build products: large trees, secrets, per‑machine data. There, make the rendered file read‑only, and add a post‑checkout hook so clones are not dangling.

4 · Freshness and the loop

Hash the inputs, not the generator

Three freshness models appear in the sources. An mtime chain, as in make, ninja and Observable. A hash of the generator text, as in org‑babel. A hash of the inputs' content, as in knitr's cache.extra and redo‑stamp. Only the last one is correct for "the folder changed": when a new file appears, neither the template nor the marker changes. Hash the generator expression plus the content of every declared input, and store the result in the closing marker.

The loop problem is separate. A daemon that writes what it watches retriggers itself. Four mechanisms from the watcher and build‑tool world, combined, cut it.

Each piece is lifted from something shipped. redo hands every script a temp path and renames it into place only on exit zero. ninja's restat and redo‑stamp treat an unchanged output as never having needed a rebuild. watchman runs a single instance of a trigger "to avoid fork‑bomb style behavior in cases where your trigger also modifies files", with a 20 ms settle. chokidar's atomic option exists because editors delete and re‑add on save. notify's docs say the same in plainer words.

A watcher is a convenience layer, not the foundation. cog, mdsh, embedme and markdown‑magic all rely on a no‑diff assertion in CI or pre‑commit. Ship run, check, clean and watch, and make check the entry point everything else is built on.

5 · What to borrow

Observable's loaders for the source layer, cog's markers for the grammar

Observable Framework never rewrites markdown. The page names a file. If the file does not exist, a loader with a double extension is found by naming convention, run, and its stdout is cached. The cache is fresh when its mtime is newer than the loader's. Three concerns the sketch bundles together are separated: the reference, the producer, and the freshness rule.

Marker grammar · from cog and markdown‑magic

<!-- computed sql db=app.db -->
| name  | count |
|-------|-------|
| docs  |     2 |
<!-- /computed sum=3f0a91c2 -->

Namespaced word, attributes in the opener, hash in the closer. Match the token anywhere on the line and keep the line's prefix and suffix, so /* computed */ and # computed use the same parser.

Formatter survival · from prettier and all‑contributors

<!-- prettier-ignore-start -->
<!-- computed tree src=./src -->
   Do not edit; regenerated by computed -->
…
<!-- prettier-ignore-end -->

Prettier's range‑ignore was designed for exactly this, for all‑contributors and markdown‑toc. A "do not edit" sentence in the marker is cheap insurance against humans and agents deleting it.

Hand‑edit protection · from cog

$ computed check
CLAUDE.md:14 region "tree" was edited by hand
  delete the sum to unprotect, or run `computed run --force`
exit 1

cog refuses to overwrite a region whose checksum no longer matches. Everyone else silently clobbers. Refusing is the safer default for a file agents also edit.

Failure · from bashup/mdsh, redo, Observable

$ computed run
CLAUDE.md:14 region "sql": sqlite3 exited 1
  no such table: files
  region left unchanged (sum=3f0a91c2)

All three replace the output only on success. A failing renderer must leave the last good region in place and report on stderr, never blank the region.

6 · Renderers

Two tools are both the query engine and the table renderer

sqlite3 and duckdb emit markdown tables natively, and duckdb queries CSV, JSON and Parquet files directly. For the tabular cases that collapses data source and renderer into one process. For diagrams, the two sink modes in the sketch already exist as two outputs of the same DSL: keep the mermaid text in the region, which GitHub renders, or run mmdc and embed an image reference.

7 · Beyond markdown

The marker needs a comment syntax. Two formats have none.

cog proves the grammar generalises: the marker is matched anywhere in a line, and a shared prefix is stripped from every line of the region, so the same tool serves C, SQL, YAML and HTML. The limit is not the tool but the format. JSON and CSV have no comment syntax, so a marker would corrupt the data. There, the answer is whole‑file generation from a template, which the copy‑mode layout already provides.

8 · Decisions

Five choices the sources do not make for you

Open questions with no precedent in the survey: whether regions may nest (none of the tools allow it), how one region can consume another as input (marimo's dependency graph is the model), and whether a hand‑edited region should be an error, as in cog, or silently overwritten, as everywhere else.
