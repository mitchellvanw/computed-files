Computed Markdown

We surveyed about forty tools that put generated content into files, and tested the symlink layout in a scratch repository. The template model holds up. The symlink does not, and we can say exactly where it fails.

Why compute it What exists The symlink Freshness What to take Renderers Other formats What is left

What we found

  • Rewriting a marked region in place is solved. cog, mdsh, markdown‑magic, doctoc and terraform‑docs all do it, and markdown‑magic already ships the folder‑tree case as a transform called fileTree.
  • Nobody ships a watcher that rewrites the file it watches. Every rewriter runs on demand with a check mode for CI. Every live system writes to a separate file.
  • A symlink at the canonical path leaves a fresh clone with a dangling file. Git stores the link as a 20‑byte blob holding the link text. If the target is ignored, there is nothing behind it.
  • A hardlink fails on the first atomic publish. After one rename(2) in our scratch repository, the symlink read the new content and the hardlink still read the old.
  • Freshness has to hash the inputs' content. An mtime chain or a hash of the generator both miss a new file appearing in the tree, because nothing in the template changed.
  • The link problem is a git and GitHub problem, not a Claude Code problem. Claude Code follows symlinks and strips block‑level HTML comments before injecting CLAUDE.md, so markers cost no tokens.

This page walks the sketch's components in order: why compute at all, what already exists, whether the canonical file should be a link, how to stay fresh without a feedback loop, what to take from the prior art, which renderers do the work, whether any of this survives outside markdown, and what is left to decide. The companion note carries the citations. We claim nothing here that is not sourced there.

1

Why compute it instead of asking the agent?

The case that started this is the folder tree in a CLAUDE.md. It is wrong the moment someone adds a file. An agent can be told to fix it, but that spends tokens on every run and still depends on the agent noticing. A computational fix has four parts: a data source (a directory, a CSV, a SQL query, a shell command), a renderer or sink (a markdown table, a fenced block, a mermaid diagram as text or as an image), a watcher that notices when the template or the data changes, and a layout that decides where the rendered file lives.

The template is hand‑written prose plus markers that say where computed content goes and what produces it. A process materialises a rendered file from it. In the original sketch, the canonical path is then a symlink to that rendered file. Section 3 is about that last step.

This may look like a lot of machinery for a folder tree. It is, and the folder tree is only the first case. The same shape covers a row count from a database, a table from a CSV, or a diagram that should follow the code. What the cases share is that the truth lives somewhere else and the document is a view of it.

GitHub does not render them, prettier leaves them alone inside its range‑ignore, and Claude Code strips them before injection.

2

What did people already build?

Two questions sort every tool we found. Where does the output live, in the same file as the source or in a separate one? And when does the tool run: on demand, at render time, or continuously? Every markdown rewriter lands in one cell, same file and on demand. Every live system lands in the opposite corner. One cell is empty, and it is the cell the original sketch was aiming at. We think the cause is the self‑write loop covered in section 4, not a lack of interest.

Four tools we would read in full before writing a line:

  • cog works on any text file. Its markers match anywhere on a line, so //[[[cog and /* [[[cog */ both work, and with -c the closer becomes [[[end]]] (sum: …). Hand‑edited output fails the next run with "Output has been edited!"
  • markdown‑magic already ships a fileTree transform. That is the motivating case, done, in a tool with a 2026 commit.
  • org‑babel has all three ingredients together: source expression next to output, output written back into the file, and a SHA1 that skips work. It has no daemon, and it hashes only the block text, not the files the block reads.
  • Observable Framework data loaders separate the reference, the producer and the freshness rule. Section 5 draws the mechanism.

3

Should the canonical file be a symlink?

The case for the link is real. Nix's result link, home‑manager generations, Stow and Bazel's convenience links all use the same shape: the link is the handle people touch, each target is immutable, and publishing a new version means re‑pointing the link. That gives atomic swaps and a clean line between what is edited and what is generated. We went in expecting to keep it.

None of those tools put the link at a path that other tooling treats as source. A CLAUDE.md is exactly such a path, and that is where it comes apart.

There are five places the rendered file can go, and each fails in its own way. A symlink to an ignored build directory gives a fresh clone a dangling link, shows GitHub the link text, and on Windows with core.symlinks off checks out as a text file containing the path. A symlink to a committed target resolves everywhere, but the repository now holds template, output and link, and the link says nothing the committed output does not. A hardlink breaks on the first publish, for the reason drawn below. Claude Code's @import gives per‑region granularity with no rewriting, and only Claude Code understands it. Or write the rendered file at the canonical path and commit it.

That last one is what gomplate, quarto, mermaid‑cli and Style Dictionary do. It is the one we recommend.

A hardlink looks like the escape hatch and is not. Atomic publish means writing a temp file and calling rename(2), which swaps the directory entry and leaves the inode behind. A hardlink is a second name for the inode, and the inode we care about has just been abandoned. We checked this rather than trust the reasoning: after one publish in a scratch repository, the symlink read the new content and the hardlink still read the old.

So: keep template → render and drop the link. Write the rendered file at the canonical path via temp file and rename(2), commit it, put a generated‑from banner on line one, and ship a check command that fails CI on drift. This is the original sketch minus one step.

We would keep the symlink layout as a per‑file opt‑in for outputs that really are local build products: large trees, secrets, per‑machine data. There, make the target read‑only so an editor's rename‑on‑save fails loudly instead of detaching the link, and add a post‑checkout hook so clones are not dangling.

What this does not settle is whether rendered output belongs in every diff. In copy mode it does. If that noise costs more than clone‑and‑go is worth, symlink mode is the honest choice, and the price is the hook.

4

How does the file stay fresh without waking itself up?

Three freshness rules show up in the sources. An mtime chain, as in make, ninja and Observable. A hash of the generator text, as in org‑babel. A hash of the inputs' content, as in knitr's cache.extra and redo‑stamp. Only the third is right for "the folder changed". When a file appears, neither the template nor the marker changes, so the first two rules see nothing. This is the one place where the most popular tools are wrong for our case. Hash the generator expression plus the content of every declared input, and store the result in the closing marker.

The loop is a separate problem. A daemon that writes what it watches wakes itself up. No single tool solves this, but four of them each solve a piece, and the pieces compose.

Each piece is lifted from something that ships. redo hands every script a temp path and renames it into place only on exit zero. ninja's restat and redo‑stamp treat an unchanged output as never having needed a rebuild. watchman runs one instance of a trigger at a time, in its own words "to avoid fork‑bomb style behavior in cases where your trigger also modifies files", with a 20 ms settle. chokidar's atomic option exists because editors delete and re‑add on save. notify's documentation says the same in plainer words.

A watcher is a convenience, not the foundation. cog, mdsh, embedme and markdown‑magic all rest on a no‑diff assertion in CI or pre‑commit, and none of them has a daemon. Ship run, check, clean and watch, and build the last three on the first two.

5

What should we take from the prior art?

Observable Framework never rewrites markdown. A page names a file. If the file does not exist, a loader with a double extension is found by naming convention, run, and its stdout is cached. The cache is fresh while its mtime is newer than the loader's. Three things the sketch bundles are held apart: the reference, the producer, and the freshness rule. We would take the first two and replace the third.

Marker grammar · from cog and markdown‑magic

<!-- computed sql db=app.db -->
| name  | count |
|-------|-------|
| docs  |     2 |
<!-- /computed sum=3f0a91c2 -->

A namespaced word, attributes in the opener, the hash in the closer. Match the token anywhere on the line and keep the line's prefix and suffix, so /* computed */ and # computed go through the same parser.

Formatter survival · from prettier and all‑contributors

<!-- prettier-ignore-start -->
<!-- computed tree src=./src -->
   Do not edit; regenerated by computed -->
…
<!-- prettier-ignore-end -->

Prettier's range‑ignore was written for exactly this, for all‑contributors and markdown‑toc. A "do not edit" sentence inside the marker is cheap insurance against people and agents deleting it.

Hand‑edit protection · from cog

$ computed check
CLAUDE.md:14 region "tree" was edited by hand
  delete the sum to unprotect, or run `computed run --force`
exit 1

cog refuses to overwrite a region whose checksum no longer matches. Every other tool overwrites without comment. For a file that agents also edit, refusing is the safer default.

Failure · from bashup/mdsh, redo, Observable

$ computed run
CLAUDE.md:14 region "sql": sqlite3 exited 1
  no such table: files
  region left unchanged (sum=3f0a91c2)

All three replace the output only on success. A failing renderer leaves the last good region in place and reports on stderr. It never blanks the region.

Which renderers do the work?

Two of them are both the query engine and the table renderer. sqlite3 and duckdb emit markdown tables natively, and duckdb reads CSV, JSON and Parquet directly, so for the tabular cases the data source and the renderer are one process. For diagrams, the two sink modes in the sketch already exist as two outputs of the same DSL: keep the mermaid text in the region, which GitHub renders, or run mmdc and embed an image reference.

Does any of this survive outside markdown?

Most of it. cog shows the grammar carries: the marker is matched anywhere in a line, and a shared prefix is stripped from every line of the region, so one tool serves C, SQL, YAML and HTML. The limit is the format, not the tool. JSON and CSV have no comment syntax, so a marker would corrupt the data. For those the answer is whole‑file generation from a template, which the copy‑mode layout already provides.

What is still ours to decide?

Five choices the sources do not make for us. We have a recommendation for each, and the second column shows who disagrees.

DecisionOptions seen in the wildOur recommendation
Layoutin‑place markers (cog, mdsh) · template → canonical path (gomplate, quarto) · symlink to build product (Nix) · @import sidecar (Claude Code)Template → canonical path by default. Symlink as a per‑file opt‑in for local build products. Never a hardlink.

Three questions have no precedent in the survey. Whether regions may nest: no tool allows it, which we take as advice. How one region consumes another as input: marimo's dependency graph is the nearest model. And whether a hand‑edited region should be an error, as in cog, or overwritten, as everywhere else.

What we did not verify. Editor behaviour when saving through a symlink comes from watcher documentation, not from testing editors. Windows behaviour comes from git's and Claude Code's documentation; we did not run a Windows checkout. "Nobody ships this" covers the tools we surveyed, which is not every tool. The symlink, hardlink and Claude Code findings were tested locally and we would stand behind those.

Open the file and the tree is right. That is the whole product. Everything above is plumbing to make it true without anyone remembering to run anything.
